## 0. 前提、假设与现状基线

### 0.1 需要标注的上下文假设（如与实际不符请指出，我据此调整）

| # | 假设项 | 假设值 | 若不符的影响 |
|---|---|---|---|
| A1 | 平台形态 | **移动端优先的 Web App（PWA）**，浏览器即用；本轮不做原生 App 与小程序 | 若要做小程序/原生，§5 阶段 2 起需拆 UI 层、引入 OAuth 体系，工期 +30% |
| A2 | 部署形态 | **自托管优先**（个人/小团队，单人或百人级并发），可 Docker Compose 一键起 | 若要 SaaS 多租户，需引入租户隔离、计费、配额，架构需重做一档 |
| A3 | 目标用户 | 中文用户为主，**非运动员的普通减脂人群**（25–45 岁），日均使用 3–5 次 | 若转向垂直（如糖尿病/孕产），营养素阈值与合规要求完全不同 |
| A4 | 商业性质 | 现阶段自用/作品集/B端演示，**非医疗级产品**，不出具诊疗结论 | 若宣称医疗用途，需走二类医疗器械或互联网医疗资质 |
| A5 | 技术栈约束 | **保留现有** Vue3 + Vite + Pinia + Vant + FastAPI + SQLAlchemy + Pydantic 组合，做增量演进而非重写 | 若要改 React/Next 或 Go 后端，等于项目重启 |
| A6 | AI 供应商 | 以**国产可免费或低成本模型**为主（智谱 GLM 等），需保留 OpenAI 兼容端点能力 | 若指定海外模型，需重估数据出境合规与成本 |

### 0.2 现状基线（已核对代码与文档）

**已有能力**：账号注册登录（JWT）· 首采资料与 BMR/TDEE/推荐热量 · 饮食记录（文字 + 拍照双模态，AI 识别后必须用户确认才落库）· 体重记录（同日覆盖）· 运动（MET 估算）· 饮水（体重×35ml）· 打卡与成就 · 电商式统计（日/周/月趋势、营养分析、周报）· AI 一日食谱 + 多轮对话（SSE）+ 每日复盘 · 运行时配 Key（三套能力独立，加密落库）· 双主题 · 单端口生产部署 · 一键脚本（start/deploy/stop）· 演示数据生成器 `seed_demo.py`。

**现存关键短板**（升级要解决的，按严重度排序）：

| 级别 | 短板 | 后果 |
|---|---|---|
| S1 | **无食物主数据**：每条记录手工填全部营养字段 | 记录成本高 → 长期留存断崖；营养数据不可信、不可复用 |
| S1 | **AI 识别数值直接入库、无校验与无对照** | 数值漂移不可控，用户不知道该不该信 |
| S2 | **目标是静态的**：注册时算固定值，体重变化不回写 | 平台期无解释，用户流失 |
| S2 | **图片 >5MB 依赖前端压缩，无服务端持久化策略** | 换机/清缓存即丢；无缩略图，列表渲染重 |
| S2 | **提醒能力缺失** | 依赖用户自觉，打卡连续性差 |
| S3 | **数据无法进出**：无导出、无外部设备导入 | 数据锁定焦虑，迁移成本高 |
| S3 | SQLite 无迁移（靠 `create_all`）、无迁移脚本 | 多人协作/回滚困难 |
| S3 | 无 AI 调用日志与成本观测 | 排查与成本控制靠猜 |

## 1. 项目定位与品牌

### 1.1 定位重述（一句话）

> **知食（NutriMind）：一款真正「看懂你怎么吃」的 AI 减重教练——让一条餐食记录的成本压到 15 秒内，并把冗余的记录数据翻译成每天一条可执行的建议。**

差异化三要点（对应三大久攻不破的痛点）：

| 痛点 | 行业现状 | 本产品主张 |
|---|---|---|
| **记不住 / 记不动** | 主流 App 仍是「搜索→选条目→选份量」多步，抬手成本 30–47 秒 | 拍 / 说 / 拍照三通道 + 常用餐一键复制，目标中位记录耗时 ≤ 15s |
| **不知道该信谁** | 众包数据库同菜多值，MyFitnessPal 第三方评测误差约 ±18% | 每条 AI 识别都给**置信度 + 可对照的分量参考**，用户可改且系统记住你的改法 |
| **平台期没人解释** | 目标热量写死 | **自适应 TDEE**：用你的真实摄入 + 体重斜率反推代谢，每周自动校准目标（MacroFactor 式） |

**开源侧的三条结论**（直接指导设计）：
1. **数据模型比功能多更重要**：wger / Tandoor 的共识是——食物主数据、份量单位、换算链必须先立起来，否则每个上层功能都在重复造轮子。这印证了 §0.2 的 S1 短板是第一优先级。
2. **自托管产品的交付标准是 Docker 化**：lyftr、wger、Tandoor 全部以 Compose 一键起为默认体验，我们当前的 `deploy.bat` 单端口方案适合 Windows 本地演示，但不够「产品化」，应在 P0 补容器化。
3. **许可合规要提前算清**：AGPL 项目只能用其设计思路，不能抄代码；我们若走 MIT/Apache 更利于后续商业化。

## 3. 功能升级清单（按优先级分阶段）

优先级口径：**P0 = 不做则后续全部受阻的地基；P1 = 产品差异化与用户感知最强的部分；P2 = 锦上添花或需额外投入的功能**。

### 3.1 P0 阶段一：数据地基（食物主数据 + 份量 + 搜索）

**为什么先做**：所有上层智能都建立在「有可信、可复用的食物条目」之上。当前手工填五个营养字段的模式不具备长期可用性。

| 编号 | 功能 | 说明 | 借鉴来源 |
|---|---|---|---|
| F1.1 | **食物主数据模型** | `food_item` + `food_nutrient`（每 100g 口径）+ `food_portion`（份量单位↔克重换算）+ `food_alias`（别名/方言，支撑中文搜索） | wger / Tandoor 的单位抽象 |
| F1.2 | **三层数据策略** | ①系统内置库：中国常见食材与家常菜 ≥ 1,500 条（标注来源 `system/usda/off/user`，并可继承 OFF / USDA 的公开子集；②用户自定义菜品：可保存自己的「常吃的菜」并复用；③外部：条码走 OFF，补全走 USDA | OFF/USDA 调研 + 薄荷「中餐适配」启示 |
| F1.3 | **份量与单位换算** | 支持「一碗/一份/一个/100g/中份」等中文常见单位，每个食物可配多个常用份量；录入只需选食物 + 选份量 + 数量 | Tandoor 换算链 |
| F1.4 | **中文优先的搜索** | 别名、拼音首字母（`hxg`→红烧肉）、常用度排序（按自己历史记录频次排序，而非通用热度） | 竞品普遍未做「个人热度排序」，这是可打的差异点 |
| F1.5 | **食物画像页** | 单条食物展示每 100g 营养 + 常见份量预览 + 「你上次吃了 1.5 份」+ 纠错入口（`food_correction` 记录用户对 AI/系统值的修改） | fud-ai「用户确认」思想扩展到纠错闭环 |
| F1.6 | **数据质量与置信度** | 每条食物带 `confidence`（0–1）与 `source`，UI 上轻表达（如数据密度条），AI 结果默认中低置信 | 众包库污染的反面教训 |

### 3.2 P1 阶段二：记录摩擦压到最低（三大录入通道）

目标：**常见餐 median time-to-log ≤ 15 秒**（对照 MyFitnessPal 手动 10–20s+Lose It 5–10s 的区间，取可达的中上水位）。

| 编号 | 功能 | 说明 | 借鉴来源 |
|---|---|---|---|
| F2.1 | **拍照识别增强** | 单次识别返回**多候选**（每道菜 top-3）+ 份量默认建议 + 逐项可改 + 批量确认；识别结果先写 `draft` 不落库 | fud-ai 多候选 + 现有已是双模态的延伸 |
| F2.2 | **识别结果结构化约束** | LLM 输出强制 JSON Schema，服务端做**范围校验**（单位热量、营养比合理性），越界则降级为「需手动确认」，避免幻觉数值入库 | 行业 AI 应用普遍做法 |
| F2.3 | **一句话自然语言录入** | 「半碗米饭两个鸡蛋一份青菜」→ 解析成结构化条目；LLM 解析 + 词典兜底双通道；失败可降级到搜索 | MFP Premium 语音/NLP 的对位 |
| F2.4 | **常用餐与历史复制** | 「我的常吃」「上周同一天」「复制昨日午餐」一键复用，支持组合套餐（`meal_combo`） | Lose It! 的 recurring meal 思路 |
| F2.5 | **离线队列与占位** | PWA 离线缓存食物库，断网时把记录写入本地队列，恢复后自动回传并保证幂等 | OpenNutriTracker / waistline 的离线优先 |
| F2.6 | **运动记录升级** | MET 字典表化（可维护）+ 「我做了 X 分钟 Y」的口语化输入 + 与当日热量缺口联动展示 | wger 的训练/代谢拆表 |
| F2.7 | **识别精度可观测** | 建立 100 道家常菜的内部评测集，跟踪 MAE/MAPE，每次改 prompt/model 必跑回归 | Cal AI/PlateLens 的精度宣称反向启发 |

### 3.3 P1 阶段三：自适应目标引擎（产品的「第二大脑」）

目标：**每周自动把目标校准到可信水位，并在平台期给出解释**。

| 编号 | 功能 | 说明 | 借鉴来源 |
|---|---|---|---|
| F3.1 | **真实 TDEE 反推** | 用「累计摄入 vs 体重斜率」反推个人实际能量消耗（`energy_coefficients` 表），与静态公式值并列展示，让用户看到「你的身体实际是怎么算的」 | **MacroFactor 核心机制** |
| F3.2 | **目标周校准** | 每周自动调整推荐热量（限幅 ±150 kcal/周），保留每次调整的原因与证据（体重斜率、达成率），可回滚到手动锁定 | 同上 |
| F3.3 | **减重速率约束** | 目标速率限制在体重 0.5–1%/周，越界自动提示并给出更温和方案（健康护栏） | 健康合规底线 |
| F3.4 | **目标达成预测** | 基于当前斜率预测达标日期 ± 区间带（而非单点预测，避免虚假精确） | 体重管理的普遍需求 |
| F3.5 | **食谱生成升级为可落套餐** | AI 生成的三餐可直接「一键写入今日计划」→ 用户点一下就能变成实际记录；同时约束：热量目标、宏量分配、忌口、偏好、常见食材 | 现有 `generate-plan` 的闭环补全 |
| F3.6 | **建议可解释** | 每条推荐必须附带一句「为什么」：「因为你本周工作日晚餐占 46%，建议把碳水前移到午餐」 | 无解释的推荐 = 无效推荐 |

### 3.4 P1 阶段四：可视化与自动复盘

| 编号 | 功能 | 说明 |
|---|---|---|
| F4.1 | **体重曲线去噪** | 7 日移动均值 + 异常点修正（如称重时间差异），主曲线显示趋势线、原始数据以淡点显示；明确标注「单日波动 ≠ 变化」 |
| F4.2 | **多指标叠加** | 体重 / 体脂 / 腰围 / 骨骼肌同图切换，支持目标线与里程碑标记 | openScale 多维思维 |
| F4.3 | **每日洞察卡** | 首页产出 1 条可执行洞察（而非罗列数字）：「今天蛋白质缺口 27g，晚餐加一份鸡胸就够了」 |
| F4.4 | **自动生成周报** | 周一推送：热量达成率、体重斜率、TOP3 高热量来源、下周目标调整说明；可导出图片卡片 | wger 报表思路 |
| F4.5 | **对比式复盘** | 「与上周相比」「与第一个月相比」的时间段对比视图，让长期坚持可见 |

## 4. 技术方案（只给设计结论，不写代码）

### 4.1 技术栈建议

| 层 | 现有 | 建议 | 理由 |
|---|---|---|---|
| 前端框架 | Vue 3 + Vite + Pinia + Vant | **保留**，Vant 继续使用但**弱化其默认视觉**（令牌覆盖），新增组件自建 | 重写收益远低于成本；组件脏 few 的地方用自有 token 覆盖即可 |
| 状态/数据获取 | Pinia + 手写 axios 封装 | 保留 Pinia；**收敛出统一的 query 层**（请求去重、缓存 TTL、错误重试策略一致化） | 避免各页各写一套 loading/error 行为 |
| 离线与 PWA | 无 | 新增 **PWA**（vite-plugin-pwa）+ 本地队列（IndexedDB）+ 食物库快照缓存 | 支撑「断网也能记」这一核心体验，也对齐离线优先类竞品 |
| 图表 | ECharts | 保留，但**抽一层 Chart 适配接口**，让图表可被替换为轻量实现 | 目前 StatsPanel 打包体积偏大（1MB+），留替换余地 |
| 后端框架 | FastAPI + Uvicorn | 保留；**三层严格化**：router（只做校验与序列化）→ service（业务规则与编排）→ repository（数据访问与缓存） | 现状 routers 里已混入逻辑，随功能翻 3 倍会失控 |
| ORM / 迁移 | SQLAlchemy 2.0 + `create_all` | 保留 SQLAlchemy，**新增 Alembic** 并锁定所有 schema 变更走迁移 | 团队协作与回滚的刚需 |
| 数据库 | SQLite | **双轨**：默认 SQLite（自托管零运维）→ 规模上来切 **PostgreSQL**（预留 `PG` 分支：JSONB、全文检索、pgvector） | 通过 DAO 层与类型约束保证可切换；不要一次上 Postgres 增加运维负担 |
| 缓存 / 队列 | 无 | 初期 **APScheduler（进程内定时）**；出现多实例时切 Redis + RQ/Celery | 提醒、周报、数据同步都属于异步；先轻量后演进，避免过早引入重依赖 |
| 全文/向量检索 | 无 | 向量：**sqlite-vss（SQLite）→ pgvector（PG）**；全文：PG 全文或 表级 LIKE + 别名表（起步够用） | 支撑「这件事我上次吃了什么」的语义召回 |
| 文件存储 | 本地 `uploads/` | 抽 **Storage 抽象**（LocalAdapter / S3Adapter 可选），并生成多尺寸 WebP 缩略图 | 迁移无忧；列表页加载从原图改为缩略图，直接压掉首屏流量 |
| AI 网关 | 已有 provider 抽象 | **保留并强化**：统一 provider 注册、温度/超时/重试策略外置、**结构化输出契约**、调用日志与成本记录、失败降级链 | 现有三套配置的设计正确，缺的是观测与契约 |
| 部署 | Windows 脚本 + 单端口 uvicorn | **新增 Docker Compose**（web / worker / Redis / 可选 PG）+ Caddy/Nginx；Windows 一键脚本继续保留用于本地演示 | 对齐自托管项目交付标准 |
| 观测 | 部分结构化日志 | 结构化 JSON 日志 + request_id + **AI 调用追踪**（模型/耗时/token/成功与否）+ 关键端点 p95 指标 | AI 功能是最大的不确定成本，必须可观测 |
| 测试 | 冒烟/手工 | Pytest（service 层为主）+ **营养计算 golden tests** + Playwright 关键路径冒烟 +AI 评测集回归 | 让改造可验证、可回滚 |

### 4.4 模块划分与职责边界

| 模块 | 职责 | 不负责 |

| `auth` / `user` | 身份、档案、偏好、met 计算输入 | 不做目标自适应（交给 energy） |

| `energy` | BMR/TDEE 静态估算 + 自适应反推 + 每周校准 + 目标历史 | 不做 UI 展示 |
| `planning` / `recommendation` | 规则引擎 + LLM 混合推荐；食谱生成与落套餐；忌口/偏好约束；可解释输出 | 不绕过 nutrition 自己算数 |

| `integrate` | 导入导出作业、字段映射预览、格式转换 | 不静默写库 |
| `ai` | 网关、provider 抽象、结构化输出契约、降级链、调用日志与配额 | 不承载业务规则 |
| `ops` | 健康检查、备份、迁移、审计、成本看板 | — |

### 阶段 0：工程地基（约 1.5 周）

**产出物**：Alembic 迁移脚本与基线 · 分层重构后的目录约定 · 统一错误处理与结构化日志 · `/health`、`/ready` · Docker Compose + README · CI（build + pytest + 冒烟）· 配置启动校验。

**验收标准**
1. 全部 schema 变更只能通过迁移，删除 `create_all` 依赖；`alembic upgrade head` 从空库到最新无报错，且**回滚版本可用**。
2. `docker compose up` 起全套，本地首次访问即可完成初始化；Windows 一键脚本仍可用。
3. CI 绿：后端 pytest 通过、前端 build 通过、Playwright 冒烟 5 页无 page error（沿用 `docs/升级方案.md` §5 口径）。
4. 所有端点错误统一结构、无堆栈泄漏；request_id 贯穿日志。

### 阶段 1：食物数据引擎（约 3 周）—— 最关键的 21 天

**产出物**：食物主数据四张表与迁移 · 内置中文食物库（≥1,500 条，含别名与常用份量，标注来源）· 搜索 API（中文/拼音/别名/个人热度排序）· 食物画像页 · 记录改造：选食物+份量即会自动出营养 · 用户自定义菜品与纠偏记录。

**验收标准**
1. **记录成本下降可量化**：随机抽 20 道常见餐，从「打开 App 到记录完成」的中位耗时 ≤ 25 秒（当前需手填 5 个字段，预计 60 秒以上）。
2. 搜索 top-3 命中率 ≥ 90%（自建 100 条 query 评测集，含拼音与别名）。
3. `nutrition` 服务 golden tests：30 组（食物×份量×数量→营养）结果与手算一致，误差 < 0.5%（舍入口径统一到 1 位小数）。
4. 老数据可通过一次性迁移脚本挂载到 `food_item`（无法匹配的保留自由文本）。

### 阶段 2：低摩擦记录（约 3 周）

**产出物**：拍照多候选 + 逐项编辑 + 批量确认 · 结构化 AI 输出 + 范围校验 + 越界降级 · 一句话自然语言录入 · 常用餐/历史复制 · PWA 离线队列 · 运动 MET 字典 · AI 评测集与回归脚本。

**验收标准**
1. **time-to-log ≤ 15 秒**（拍照路径，20 次常见餐中位数；不含模型排队时间，AI 等待期间允许用户先发走再做修正）。
2. AI 输出 100% 通过 schema 校验；超出营养合理区间的识别结果自动降级为「请手动确认」，**无越界数值入库**。
3. 自建 100 道家常菜评测集：能量 MAE ≤ 15%，且每次 prompt/model 变更后自动回归，退化 >3pp 则阻断发布。
4. 断网写记录 → 恢复网络后自动同步且**不产生重复记录**（幂等键验证通过）。

### 阶段 3：自适应目标引擎（约 2.5 周）

**产出物**：`energy_coefficients` 与 `target_history` · 真实 TDEE 反推算法（含至少 14 天数据冷启动策略）· 每周目标自动校准（限幅 ±150 kcal）· 目标可手动锁定/回滚 · 食谱一键落今日记录 · 每条建议的可解释文案模板。

**验收标准**
1. 用 `seed_demo.py` 生成的 30 天数据回放：反推 TDEE 与构造真值误差 ≤ 10%。
2. 目标调整 **必有理由 + 必有证据**（界面可见"为什么"），且可在设置中一键回到上次目标。
3. 减重速率超 1%/周时自动提示降温方案并默认采用保守值（健康护栏通过用例全覆盖）。
4. AI 生成的食谱可在 2 次点击内变成当日真实记录，且热量与 Macro 与目标偏差 ≤ 10%。

### 阶段 4：可视化与自动复盘（约 2 周）

**产出物**：体重曲线去噪（7 日移动均值 + 异常修正）· 多指标叠加与目标线 · 每日洞察卡 · 周一自动周报（内含下周目标调整说明）· 时间段对比视图。

**验收标准**
1. 同一份含噪声数据，趋势线与实际走向一致（人工目视 + 3 组构造数据校验）。
2. 每日洞察卡必须**可执行**（给出具体食物/行为，而非复述数字）；随机 10 天中有 ≥ 8 天产出有效洞察。
3. 周报可导出为图片卡片；周报生成失败不影响主流程（降级为"本周周报生成失败"提示）。

### 阶段 5：提醒与数据生态（约 2 周）

**产出物**：提醒规则引擎 + 静默时段 + 去重日志 · 浏览器通知通道 · CSV/JSON 导出 · PDF/图片周报导出 · 健康平台导入（先做 CSV/XML 手动上传 + 映射预览）· 条码对接 Open Food Facts（P2 部分）· 图片缩略图与存储抽象。

**验收标准**
1. 提醒在设定时间 ±3 分钟内触发，同一天同一类型**不重复打扰**；静默时段无推送。
2. 导出格式自描述（含表头与单位），可被重新导入且数据等价。
3. 导入流程必须经用户确认的映射预览，**不允许静默写入**；导入失败可回滚。
4. 列表页加载走缩略图，首屏图片流量下降 ≥ 70%。

### 阶段 6（可选，超出主线）：触达增强与扩展设备

Apple Watch / WearOS 快捷录入 · 蓝牙体脂秤对接 · 家庭多人档案 · 数据进入 RAG 知识库。此阶段视阶段 2/3 的数据与反馈再决策，**不在本次立项范围**。

## 6. 风险与开放问题

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| **AI 识别精度不足**（中餐混合菜最难） | 用户一次错记即流失 | 多候选 + 可编辑 + 纠偏记忆 + 精度评测集常态化；明确在 UI 上做"预估"表达而非"精确"承诺 |
| **中文食物数据无免费权威源** | 数据质量是产品上限 | 三层策略 + 用户自定义沉淀 + 对每条数据标注来源与置信度；关键食材用中国食物成分表纸质/公开资料人工录入并留档 |
| **数据合规与人身安全** | 极端节食误导风险 | 产品内强制健康护栏（下限热量、最大减重速率）；免责声明不涉足医疗结论；未成年人/孕产妇场景明确提示就医 |
| **许可合规**（AGPL 项目的借鉴边界） | 法律风险 | 只借鉴数据模型与交互思想，不复用代码；核心依赖优先 MIT/Apache |
| **SQLite 并发与迁移** | 多人同时写入锁表 | 尽快引入 Alembic；写入热点表加索引；规模增长切 PG 的开关预留 |
| **AI 成本不可控** | 自托管者成本突刺 | AI 调用全量日志 + 配额策略 + 无 Key/超限时明确降级 |
| **范围蔓延**（看到竞品就想加） | 主线延期 | 本方案已明确"暂不做"清单，任何新增项需走变更评审 |

**需要你确认的开放问题**（影响后续细化）：
1. 目标用户是否有**公斤级精度以外的诉求**（如备赛、增肌、慢病管理）？若有，目标引擎的策略会不同。
2. 是否需要**多人/家庭共享**或对外展示（会影响账号体系与数据隔离设计）？
3. 是否有**已购买/可授权的食物数据源**（若有，可显著加速阶段 1）。
4. 是否在本轮就评估**小程序或 App 外壳**？若是，UI 层需提前做组件 API 的抽象收口。

## 7. 桌面端 UI/UX 优化专项（补充要求）

> **原则：桌面端与移动端同步发布，不存在"先做手机、桌面以后再说"。**
> 桌面不是把手机屏拉宽，而是**另一套信息架构**：同一份数据、同一套接口、两套布局语言，由断点驱动。

### 7.1 为什么必须单独设计

| 维度 | 移动端（拇指驱动） | 桌面端（鼠标 + 键盘驱动） |
|---|---|---|
| 导航 | 底部 Tab，单手可达 | 左侧 Rail（216px，可折叠 72px）+ 顶栏；层级更深也能容纳 |
| 空间观 | 一屏一件事、纵向滚动 | **一屏多件事、分区并行**：趋势图 + 缺口图 + 洞察同屏可见 |
| 效率机制 | 拍照、大按钮 | ⌘K 全局搜索、快捷键、拖拽上传、Ctrl+V 粘贴、**分栏原地编辑**（不弹窗） |
| 密度 | 低密度、大纲视图 | 中高密度：表格化列表、多列卡片、行内操作 |
| 输入场景 | 随手即记（厨房/路上） | **追补与复盘**：一次性补录、批量调整、导出 |

### 7.2 五个页面的桌面形态（移动端同一套设计语言与组件的桌面变体）

| 页面 | 桌面形态 | 关键设计点 |
|---|---|---|
| **工作台（首页）** | 顶部 Hero（大环 + 结论句 + 达成预测）+ 三张快捷卡 + 双栏内容区（左：餐次流 + 营养条；右：今日洞察 + AI 食谱 + 称重迷你走势） | Hero 横向布局复用环的右侧空间放"还能吃什么"的实物参照；洞察卡作为一等公民而非角落提示 |
| **饮食记录** | **分栏**：左 餐次列表（含拖拽/粘贴上传区）+ 右 选中项**详情编辑面板**（sticky） | 桌面端禁止"点了之后弹窗编辑"——弹窗遮住列表上下文；改为原地编辑实时更新右侧数值 |
| **AI 助手** | **三栏**：会话列表 236px + 消息流（阅读列 ≤760px）+ 上下文面板 300px | 右侧常驻"今日上下文/记忆/模型"，把 AI 从聊天玩具变成带上下文的教练；⌘Enter 发送、Shift+Enter 换行 |
| **数据分析** | **仪表盘**：全局时间范围 + 4 张 KPI + 多图并列（体重趋势大图带目标线与预测区间 / 每日缺口双柱）+ 营养素达成 + 自动洞察列表 | 桌面优势就是"一次看全"，禁止为了看第二张图而滚动；悬停 tooltip 显示当日明细 |
| **设置与目标** | **两栏**：左 分组导航、右 表单面板 + 吸底保存栏 | 分组标签化，避免长单页滚动；目标调整为**自动校准 + 手动锁定**双模式，展示上次校准的理由与证据 |

### 7.3 桌面端交互约定（写进设计系统）

1. **通用导航**：左侧 Rail 可折叠，折叠态只显示图标并显示 tooltip；顶栏常驻「日期切换 · ⌘K 搜索 · 主题 · 头像」。
2. **键盘**：⌘K/全局搜索、⌘Enter 提交、Enter 发送 / Shift+Enter 换行、Esc 关闭浮层、`j/k` 上下选择列表行、`e` 编辑选中项。所有快捷键在界面上有可见提示（`<kbd>` 样式），不做隐藏彩蛋。
3. **指针反馈**：所有可点击元素必须有 hover（背景/阴影/位移三选一，禁止只用颜色变化）；行 hover 出现行内操作按钮；`:focus-visible` 统一 2px 强调色环 + 2px offset（键盘用户必须能看见焦点）。
4. **输入效率**：拖拽上传 + 剪贴板粘贴图片登记；日期选择器支持键盘输入（`9-29` 自动补全）；常用餐支持右键菜单快速复用（P2）。
5. **密度与断点**：内容最大宽度 1320px；≥1024px 双栏、≥1440px 启用右侧辅助栏；组件内部用 `@container` 查询而非只看视口；提供「舒适 / 紧凑」密度开关（紧凑态圆角收小、间距 ×0.84）。
6. **多图并列的视觉纪律**：同一屏只保留**一条强调色通道**，其余图表走中性色（参见 §1.3），否则桌面端视觉噪声会抵消掉信息密度带来的收益。
7. **空状态横向化**：桌面空态用「左图右文 + 主次按钮」横向构图（不是移动端的大幅居中堆叠）。

### 7.4 对技术方案的追加要求

- **布局层**：引入容器查询（`@container`）；响应式统一用 `width >= 1024 / 1440` 两级断点，禁止各处写死 `px`。
- **组件契约**：同一业务组件准备 mobile / desktop 两套模板，通过容器查询或 `useBreakpoint` 切换**（二选一并全项目统一，建议容器查询优先）**；禁止在服务端按 UA 判断并下发给不同组件树。
- **列表 → 详情**：桌面路由支持 `/diet?sel=<id>` 深链，便于书签与刷新保留选择；属于 §4.2「受保护契约」的新增项，需在阶段 2 一并落地。
- **表格化视图**：阶段 4 引入 `daily_summary` 后，数据页桌面形态应提供**明细表格**（可排序、可导出），手机端仍走卡片流。

### 7.5 阶段与验收追加

| 阶段 | 桌面端追加产出物 | 追加验收标准 |
|---|---|---|
| 阶段 0 地基 | 响应式骨架（Rail + Topbar + 容器查询基础设施）、双模版组件规范 | 1024/1440/1920 三档下无横向滚动、无元素重叠；键盘 Tab 顺序符合阅读序 |
| 阶段 1 数据引擎 | 桌面版食物选择器（列表 + 搜索 + 份量即时预览，表格化） | 键盘全流程可选一条食物并完成录入（不碰鼠标） |
| 阶段 2 低摩擦记录 | 拖拽上传、粘贴识别、分栏原地编辑、⌘K | **桌面 time-to-log ≤ 12 秒**（20 次常见餐中位数）；拖拽与粘贴路径均可跑通 |
| 阶段 3 自适应目标 | 设置中心桌面形态（目标双模式、校准证据面板） | 每次目标调整均可在界面上追溯到数据与理由 |
| 阶段 4 可视化 | 桌面仪表盘（多图并列）、悬停明细、导出 | 一屏内同见图 ≥ 3 张且无滚动；导出 CSV 与界面数值完全一致 |
| 阶段 5 生态 | 桌面端批量导入/导出向导（多步、可预览） | 导入预览可逐条勾选；失败行可定位并重试 |

### 7.6 追加工作量估算

桌面端并非免费赠送：**每阶段约追加 25–35% 前端工时**（双套布局 + hover/focus/键盘态 + 断点回归）。按 §5 的 14 周总盘子估算，桌面同步发布约需 **+3 至 +4 周**，合计约 **17–18 周**；若接受"移动端优先打磨、桌面端滞后一个阶段交付"，可压回到 16 周左右。

> 已有交付物：`docs/design/lightslim-ui-desktop-v0.html`（桌面端可点击原型：5 页桌面形态 + Rail 折叠 + ⌘K + 拖拽区 + 三栏 AI + 仪表盘 + Tweaks 主题/强调色/密度/动效开关）。

实测：`/push/public-key` 返回公钥、`/push/status` 返回 `running:true` 与当天 6 条计划；浏览器侧真实订阅受限于推送服务商网络（需可达 Google/Mozilla 推送通道），已在文档标注。

**② 离线写入与读数**

- `utils/offline.js`：IndexedDB 双 store——写队列（`queue`）+ 读数缓存（`cache`，TTL 12h）。
- 写：`/diet/add`、`/weight/add`、`/water/add`、`/exercise/add`、`/diet/{id}` 等记录在**明确断网**时入队，UI 提示「已离线保存，联网后自动同步」；关键是 `flushQueue`：网络恢复（online 事件 + 60s 兜底轮询）自动补发，5xx/无响应重试最多 5 次，4xx 直接丢弃并告知用户——毕竟重试一万次也成功不了。
- 读：`request.js` 对 13 个关键读数接口做响应侧写缓存；网络层故障时回退缓存（Token 失效、业务错误码不走缓存，避免用旧数据掩盖真问题）。
- 界面：`components/OfflineBar.vue` 顶部浮动状态条——「离线中 · N 条待同步 / 离线浏览中 / 立即同步」。

**③ SQLite → PostgreSQL**

- `database/db.py` 支持 `DATABASE_URL`（优先级高于 `DB_PATH`），PostgreSQL 走独立连接池参数：`PG_POOL_SIZE / PG_MAX_OVERFLOW / PG_POOL_RECYCLE / PG_POOL_TIMEOUT / PG_POOL_PRE_PING`。
- `scripts/migrate_to_pg.py`：以 **ORM 模型**（而非 SQLite 表结构）为准在目标库建表 → 按主键分页批量搬迁（每批 500）→ **`setval` 重置自增序列**（最容易漏、漏了第一条新记录就主键冲突）→ 逐表行数校验。支持 `--dry-run / --truncate / --only`。
- 搬迁用 Core `select(列名)` 而非裸 SQL：SQLite 里日期存的是 `YYYY-MM-DD` 字符串，裸取出来喂给 `Date` 列会被类型检查拒绝。
- 已用「临时 SQLite 目标库」跑通全部 14 张表 820 行并校验一致（本机无 PG 实例，PG 侧仅做干跑）。
